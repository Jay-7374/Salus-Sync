We are building a new standalone companion application called:

SALUS Sync

This is a separate project/repository from the existing SALUS healthcare web platform.

SALUS Sync will eventually become a small native Android companion app whose purpose is:

Health Connect → SALUS Sync → FastAPI Backend → Supabase → SALUS Patient Dashboard

However, we are currently implementing:

PHASE A — WEB UI PROTOTYPE

The goal of Phase A is to build and validate the complete user interface, navigation, authentication flow structure, health-data presentation, synchronization UX, and API architecture before recreating/porting the application as a native Android app using Kotlin + Jetpack Compose.

IMPORTANT:
This Phase A application runs in a browser.

A browser CANNOT directly access Android Health Connect.

Therefore:

- Do NOT attempt to implement Health Connect.
- Do NOT build fake browser integrations pretending to access Health Connect.
- Use a clearly isolated mock health-data provider for UI development only.
- Design the architecture so MockHealthDataProvider can later be replaced conceptually by HealthConnectDataProvider in the native Android app.
- Do NOT modify the existing SALUS backend.
- Do NOT create database tables.
- Do NOT create new backend endpoints.
- Do NOT implement registration.

9. BACKEND HEALTH DATA CONTRACT
=========================================================

The existing backend supports:

GET
/api/v1/health-sync/status

POST
/api/v1/health-sync

GET
/api/v1/health-metrics/latest

GET
/api/v1/health-metrics/history

Authentication:

Authorization: Bearer <access_token>

The upload body is:

{
  "records": [
    {
      "metric_type": "HEART_RATE",
      "value": 72,
      "unit": "bpm",
      "start_time": "ISO-8601 datetime",
      "end_time": "ISO-8601 datetime",
      "source": "Health Connect",
      "device_name": "HONOR Band"
    }
  ]
}

Allowed metric types:

HEART_RATE
STEPS
SLEEP
SPO2

Create TypeScript interfaces/models corresponding to these contracts.

IMPORTANT:

Do not change these contracts.

Do not invent additional backend fields.

Do not send user_id from the client.

The backend derives user identity from the JWT.
